## Backend backlog (from the audit, not built in v4.21; effort S = under half a day, M = a day or two)

Written down so nothing is lost. Order is roughly by value.

1. **"Re-upload everything from this device" button (audit item 7, S/M; done: Settings > Sync > Re-upload, `sync.resendEverything`).** After a lost or restored server, devices don't re-send because they think the server already has their data. A Settings > Sync recovery button: `db.forgetSyncedMarks()` plus `syncState` reset plus mark all media as not uploaded.
2. **Backups (audit item 7, S/M; done).** Free has no automatic database backups, and no plan backs up Storage files. The real copies are each user's devices and Export backup files. Done: `.github/workflows/backup.yml` runs `pg_dump` (postgres 17 image) nightly at 03:43 UTC and on demand, dumps the `public` schema plus `auth.users` and `auth.identities`, gzips and encrypts it (`gpg --symmetric`, AES256) and keeps it as a private workflow artifact for 30 days; with `SUPABASE_DB_URL` (Session pooler URI) or `BACKUP_PASSPHRASE` missing it ends green with a notice. The owner adds both secrets and tries it once (steps, download, decrypt and restore: `docs/sync-setup.md` section 8b). **Storage files (pictures and sounds) are NOT in the dump**; they exist only on devices and in Export backup files (Pro would not change that). In the app: Settings > Your data shows "Last backup: 12 days ago" / "No backup yet on this device", and an amber note when the last backup is over 30 days old (or none) and there are 50+ cards (`js/backup-nudge.js`, softer wording when signed in). `lastBackup` is now device-only (`LOCAL_ONLY`): a backup file lives on one device, so it is neither synced nor written into backups, and a restore does not touch it. Tests: `tests/backup-nudge.test.js`, `tests/browser/e2e-backup-note.mjs`. Still open: Pro (7 days of backups) if the app grows.
3. **Wait 30 days before deleting pictures from the server (done, client-side: `js/media-sweep.js`; synced `mdel:<id>` marks). Its protection only holds once every device runs the new version; older ones still delete at once.** `cleanMedia` removes a picture from the account right away; if another device still has a card using it, that file is gone for everybody. Mark for deletion with a date and sweep after 30 days (client or an Edge Function).
4. **Prune deleted rows (audit item 10, M; planned, parked until needed: `docs/design/prune-plan.md`).** Also prune the `mdel:` settings rows that are `null` or `'gone'` and older than about 180 days. Also: once deleted markers are pruned, "Re-upload everything" on a device that still holds a pruned deleted card would bring it back, so this item must block or rework that button. **Status (2026-10):** re-planned and still parked; only Step 0 is built (`owner.sql` shows `marker_rows`, `marker_mb`, `dead_mdel_rows`). Full plan: `docs/design/prune-plan-2026-10.md`, build trigger in `docs/design/prune-plan.md` ("Status and corrections").
5. ✅ **Overlap window when pulling (audit item 11, M; done, client only).** `seq` isn't in commit order, so with 3+ devices syncing at once a device could skip a change from a transaction that commits late. Each pull now starts behind the bookmark. After every request (page) `syncState.seqLog` gets `{ t, seq, from, n }` (time sent, bookmark after, what it asked after, rows got), saved together with the bookmark, so a pull cut off midway carries on near where it stopped. `pullStart` (js/sync-merge.js) asks after the bookmark that was current 2 minutes before the *previous* pull (a long gap between syncs doesn't shrink the window; seq numbers are shared by all accounts, so counting numbers wouldn't mean anything), but never more than 3,000 rows back (and never past the requests of the last 30 seconds), so a big download isn't read again. Re-read rows are skipped by `decide()` (same time = skip): nothing is re-pushed, counted or re-healed (`gotNotes` only counts rows that changed something). The bookmark never moves backwards; a missing or stale log (first sync, reset, older version, downgrade) starts fresh; a clock that went backwards restarts the log. Cost: about 2x in steady state; for up to 2 minutes after a big download every quick sync re-reads up to max(3,000, the rows of the last 30 seconds). No SQL change. A big download that is cut off carries on from about 30 seconds before where it stopped; those requests are marked settled once a later pull (30+ seconds after) has read their stretch again, and re-reads of settled rows are settled at once, so a cut-off download keeps moving forward (simulated, 100,000 rows: attempts of 20 pages at 1 s with 1 s between them finish in 19 attempts, 30 pages at 300 ms with 5 s between in 13). Attempts much shorter than 30 seconds move forward slowly (5 pages at 1 s, 2 s between: 196 attempts; 3 pages at 300 ms with no gap: about 16 pages per attempt gained, 48,100 rows after 3,000 attempts). Remaining tiny gap: a change numbered below the end of a page of a first download that lasts over 2 minutes, or a change still unsaved after 30 seconds while this device downloads more than 3,000 rows after the page that missed it (another device outrunning a slow save for over 30 seconds). Tests: `tests/sync.test.js` (overlap section), `tests/browser/e2e-sync-overlap.mjs`.
6. **First sync for big accounts (audit item 12, M; first part done, released in v4.30).** A heavy account is about 210,000 rows, 210 requests of 1,000, several minutes on a phone. **Measured first** (a throwaway script against a fake server with a delay per request, headless Chromium on a busy 4-core machine, so only the ratios mean something; rows: 12% cards, 12% card states, 76% review log, 5% deleted): of a 100,000-row first pull at 200 ms per request (50 s) about 27 s (54%) was saving to the database (`db.applyRemote`, about 270 microseconds a row, mostly writing the four or five indexes of each store; looking up the local copy of each row costs little: skipping every lookup changed nothing), 20 s (40%) was waiting for the network (one request after another) and about 3 s was everything else (JSON parsing, the bookmark save after each page). **Done: the next request is sent as soon as a page has arrived, while that page is being saved** (`pullPages` in `js/sync-merge.js`, which is the old loop of `sync.js` moved out so it can be tested). Before, network and database took turns; now a first download takes about the longer of the two. Before and after: 50,000 rows at 150 ms 23.9 s to 14.7 s; 100,000 at 300 ms 70.0 s to 35.6 s; 100,000 at 200 ms 50.1 s to 33.7 s; 200,000 at 200 ms 127 s to 101 s (the database was the slower side there, so only the waiting is saved). Phones are slower at the database than at waiting, so expect a smaller gain there (the saving is at most the network share, about a third to a half). **Why the item-5 rules still hold:** each request still asks after the highest number on the page before it (known when the page arrives, before it is saved); `t` is still the send time of the request that worked, and later than the previous request's, so the log stays in order; the bookmark and the log are still saved together, one page at a time, only after that page is saved, so a page whose saving fails is never logged and the next pull starts at the old bookmark (the answer already on its way is dropped); the page size of a request is the size the page before it ended with (after any halving) and the short-page check and `reach` use the size of the request that page came from; the state at the end is identical to asking one page at a time (unit test compares the full log). Re-applied rows are as idempotent as before (`decide()`). One extra request can be in flight when a pull is cut off; its answer is ignored. Memory: two pages are held at once (rows up to 60 KB each), so the peak can roughly double for large pages. Tests: `tests/sync.test.js` (end of the file: order of events, same end state as one at a time, failed save, failed request, halved page), `tests/browser/e2e-sync-overlap.mjs` (a 3,500-row first download). **Looked at and not done:** (a) *Bigger pages*: Supabase's API caps a response at its "Max rows" setting (1,000 by default) and silently returns fewer rows than asked for. The loop reads a page shorter than asked as the end of the data, so asking for more than the cap would stop the download early (it would carry on next sync, 1,000 rows at a time). Only safe if the cap were read from the server (a `Prefer: count=exact` request returns the total in `Content-Range`), and the default cap gives nothing, so not built. (b) *Skip deleted rows on a fresh device*: a "fresh" device can still hold local data whose ids exist on the server (the shared sample deck, anything made before signing in), and that data needs the server's delete markers to be removed here. Skipping the local tombstone write saves almost nothing, and a server filter (`deleted=is.false`) is unsafe: a card read live early in the download and deleted during it would get its delete number above the page that was already read, and the filter would hide it, so the card would stay here for good. A safe version needs the newest number at the start, a filtered pass up to it and an unfiltered pass after it (and a bookmark that only covers the filtered part). (c) *Review history after cards*: same filter problem (a bookmark per store); it would make the app usable sooner, not finish sooner. (d) *Compression*: browsers already ask for gzip/brotli and Supabase's gateway compresses JSON, not verified here. (e) *Saving faster*: bigger transactions, `durability: 'relaxed'` and skipping lookups made no measurable difference. (f) Progress already shows "Downloaded 42,000 changes…" every page; "of about 210,000" needs the count request above. Still open: the database side (about 60% of the time now), e.g. parallel windows by number range, which needs the log to understand several requests at once.

19. **GitHub turns scheduled workflows off after 60 days without repository activity (S; done, released in v4.30, partly manual).** GitHub's rule (docs.github.com, "Disabling and enabling a workflow"): in a public repository only, scheduled workflows are disabled after 60 days with no repository activity; GitHub doesn't define "activity" (commits certainly count). Events made by GITHUB_TOKEN don't start workflow runs, so an empty-commit keepalive is both noisy and unreliable; not used. `.github/workflows/keep-workflows-enabled.yml` runs every Monday (and on demand) with `permissions: actions: write` and no secrets, lists the repository's workflows and calls `PUT /repos/{owner}/{repo}/actions/workflows/{id}/enable` for each (itself included; the docs' permissions table allows this call with `actions: write` for an installation token such as GITHUB_TOKEN), so it switches back on any that GitHub already turned off (with a warning in the log) and re-enables the rest ahead of time, the approach of the liskin/gh-workflow-keepalive action. Workflows the owner disabled by hand (`disabled_manually`) are left alone. A failed call is counted, the loop carries on, and the run ends red with the failure issue (below). Only the states `active` and `disabled_inactivity` are enabled. The comments of the three scheduled workflows and docs/sync-setup.md (new step 8d, plus notes in 8, 8b, 8c and 9) say so. **Not proven:** GitHub doesn't document that an enable call restarts the 60-day clock, and this can't be tested before the repository has been quiet for 60 days. Also GitHub's failure emails for scheduled workflows go to the workflow's creator or last cron editor, and after a disable and enable to whoever enabled it (possibly the bot), so they can't be relied on: the backup, fuse-watch and keep-workflows-enabled workflows each end with an `if: failure()` step that opens or comments on ONE issue "Study Sprint: a scheduled job failed" (label `scheduled-job-failed`, job name and run link only; `issues: write` added to those jobs). A job GitHub switches off silently still can't report, hence the monthly Actions-tab check. **Left manual:** run "Keep scheduled jobs on" once to check it works, look at the Actions tab monthly, and re-enable by hand (Actions tab, Enable workflow) if a job shows as disabled; any commit and push restarts the 60 days for certain. An external uptime pinger for the Supabase keep-awake remains an option (not built).
