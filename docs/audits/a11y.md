# Accessibility audit: Today, Decks, Review, Import, Settings

Standard: WCAG 2.1 Level AA. Base: `main` at fd36b8c. Date: 2026-10-24.

## In plain words

The app is in good shape. Every button we found has a name a screen reader can read out. Keyboard focus shows a
visible outline everywhere we tabbed. The theme colors pass the contrast rules in all ten skin/mode pairs. Messages
("toasts") and form errors are read out. The items below are the gaps left, most important first. None of them
stops someone from finishing a review session.

## How this was checked

- **Code reading**: `index.html`, `css/styles.css`, `js/review.js`, `js/today.js`, `js/decks.js`, `js/import-screen.js`,
  `js/settings.js`, `js/sidebar.js`, `js/ui.js`, `js/a11y.js`.
- **Headless Chromium** (Playwright, 375x740, dark and light, service workers blocked, Supabase stubbed with
  `tests/browser/fake-supabase.mjs`). On each screen: every visible control checked for an accessible name and its
  size; 12 Tab presses, recording the element and its computed outline. The review flow: Start, then Space to flip,
  then 3 to grade, recording where focus lands each time.
- **Contrast**: computed from the color tokens in `css/styles.css:101-170` for all 5 skins in dark and light mode.

**Not tested**: real screen readers (VoiceOver, NVDA), 200%/400% zoom and reflow, Windows forced colors, the
desktop sidebar layout (1024px and up), and the sheets (dialogs) opened from these screens. Automated checks and
a code read cannot show WCAG conformance. **Conformance: NOT DETERMINED** until those checks are done.

## Medium

### M1. The card you flip is focusable and works like a button, but is not announced as one
- **WCAG**: 4.1.2 Name, Role, Value (A)
- **Where**: `js/review.js:280` (`<article ... tabindex="0">`), key handling at `js/review.js:921`, click at `js/review.js:327`
- **Who it affects**: screen reader users. Focus starts on the card (the probe confirmed `ARTICLE#flash role=null`).
  The reader says "article" and the question, then the hidden hint "Press Space or Enter to show the answer".
  In NVDA and JAWS browse mode, Space and Enter are often taken by the screen reader, so the hint can mislead. The real
  "Show answer" button in the bar below (`js/review.js:310`) works, but the hint does not mention it.
- **Fix**: keep the article as a plain region and make the "Show answer" button the main control. Either:
  - drop `tabindex="0"` and move first focus to the Show answer button, or
  - keep the card focusable but add `role="button"` and `aria-label="Show answer"` before flipping, with the question
    in `aria-describedby="rvQ"`. Remove them in `flip()` (`js/review.js:486` already removes `role` and `tabindex`).
- **Check**: with NVDA in browse mode, start a session. The first focus should be read as "Show answer, button" and
  Enter should flip the card.

### M2. The New / Learn / Due words are drawn by CSS, so screen readers may hear only "5 0 7"
- **WCAG**: 1.3.1 Info and Relationships (A)
- **Where**: `js/review.js:206-214` (`data-label` turned into text by CSS), group at `js/review.js:273`
- **Who it affects**: screen reader users. Text from CSS `::before` is read differently by each reader, and some
  skip it. The group label says "new, learning, due" once, but the numbers come with no words.
- **Fix**: put the words in the markup and hide the visual copy:
  `<span class="c-new"><span class="sr-only">New </span>5</span>`. Or give each span an
  `aria-label` like `"5 new"` and mark the CSS label `aria-hidden`. Keep `data-label` for how it looks.
- **Check**: VoiceOver rotor on the counts reads "New 5, Learn 0, Due 7".

### M3. The changing counts and the progress bar are not announced after a grade
- **WCAG**: 4.1.3 Status Messages (AA)
- **Where**: `js/review.js:273` (counts), `js/review.js:383` (`role="progressbar"`, which updates
  `aria-valuetext="0 of 12 cards done"` but is not a live region)
- **Who it affects**: screen reader users. After a grade, focus goes to the next card (good), but nothing says how
  many cards are left. Sighted users see the bar move.
- **Fix**: after each grade, send a short message to the existing polite region `#toastLive` (placed by `placeLive()`
  in `js/ui.js:24`, used by `toast()` at `js/ui.js:55`), for example "11 left". Do it at most once per card so it does not crowd the next question.
- **Check**: grade a card with NVDA running. It reads the new question, then "11 left".

### M4. The answer gets focus with no visible focus indicator
- **WCAG**: 2.4.7 Focus Visible (AA)
- **Where**: `css/styles.css:814` (`.rv-back:focus{outline:none}`). Focus is moved there in `flip()`
  (`js/review.js:477-500`); the probe confirmed `DIV.rv-face rv-back` has focus after Space.
- **Who it affects**: sighted keyboard users and screen magnifier users. After flipping, they cannot see where focus
  is. The next Tab goes to the rating buttons, which is hard to guess.
- **Fix**: keep no outline for mouse and touch, but show one for keyboard:
  `.rv-back:focus-visible{outline:2px solid var(--accent);outline-offset:-4px;border-radius:inherit}`. Chromium
  shows `:focus-visible` after a script focus that follows a key press, which is the case here.
- **Check**: press Space on a card. An outline shows on the answer face. Tapping the card shows none.

## Low

### L1. "Browse all cards" link is a 17px tall tap target
- **Where**: the Decks screen link "Browse all cards →" (116x17 px in the probe), at `js/decks.js:200`
- **Why**: not required by 2.1 AA (2.5.8 Target Size Minimum is new in WCAG 2.2 and asks for 24px). It is a
  stand-alone link, not part of a sentence, so 2.2 would count it.
- **Fix**: `display:inline-flex;align-items:center;min-height:44px;padding:0 4px` on that link, like `.link`
  (`css/styles.css:307`).

### L2. Several small buttons under 44px
- **Where**: `.btn.small` 34px tall (`css/styles.css:261`), `.deck .icon-btn` 36x36 (`css/styles.css:459`),
  `.filtered .link` / `.sec-head .link` / `.exam-add .link` 32px (`css/styles.css:373,376,396`), the Review header
  buttons 40x40 (`css/styles.css:307,310`). The Today, Decks and Import screens each have 4 to 10 of these; Settings
  has 51.
- **Why**: all are over 24px, so they pass 2.5.8 (WCAG 2.2) and 2.1 AA has no rule. 44px (2.5.5, AAA) helps people
  with tremors or using a phone one-handed.
- **Fix**: give small controls a bigger hit area without changing how they look:
  `.btn.small,.deck .icon-btn{position:relative}` and
  `.btn.small::after,.deck .icon-btn::after{content:"";position:absolute;inset:-5px}`. Keep enough gap between
  neighbors so the hit areas do not overlap.

### L3. Control borders are close to the 3:1 line in Forest light
- **WCAG**: 1.4.11 Non-text Contrast (AA), passes now
- **Where**: `css/styles.css:141` (`--control:#748B80`) gives 3.35:1 on `--bg #F1F6F4`. Used for text box borders
  (`css/styles.css:284`) and switches (`css/styles.css:1358`). Ember light (`#8B7D74`, 3.60:1) and Ocean light
  (`#74818B`, 3.62:1) are close too.
- **Fix**: darken Forest light `--control` to about `#677D73` (about 4:1) so a later tweak of the background cannot
  push it under 3:1. Add a unit test that checks `--control` against `--bg` and `--surface-1` for every skin.

### L4. The Decks tab uses `aria-current="true"` while the other tabs use `"page"`
- **Where**: `js/sidebar.js:162`
- **Why**: when a single deck is open, the tab says "current" with no type; elsewhere it says "current page".
  Not a failure, just inconsistent.
- **Fix**: use `aria-current="page"` there as well, or leave it and comment why ("current section").

### L5. The light/dark switch in the sidebar still says "Switch to light mode" when the skin is always dark
- **Where**: `js/sidebar.js:173-178`
- **Why**: on a skin that is locked dark, only the visual tooltip (`data-tip`) says so. A screen reader hears a
  button that does nothing.
- **Fix**: when `locked`, set `aria-disabled="true"` and `aria-label="Light mode is not available with this skin"`.

### L6. Each of the 10 hidden radio inputs in Settings is 1x1 px
- **Where**: Settings, Appearance and Scheduler choices (the `.mode` pattern, focus ring at `css/styles.css:948`)
- **Why**: this is fine. The radios are visually hidden and the whole label is the target, with the ring drawn by
  `:has(input:focus-visible)`. Recorded so an automated tool flagging "target too small" can be closed as a
  false positive.

## What already works well (keep it)

- A "Skip to page" link is the first Tab stop (`index.html:140`), and it is visible when focused.
- All header, sidebar and review icon buttons have `aria-label`, and their SVGs are `aria-hidden`.
- Rating buttons say the interval aloud ("Good, next review in 3 days") and list their shortcut keys
  (`js/review.js:440`).
- Single-key shortcuts can be switched off (WCAG 2.1.4), and Escape leaves the typing box (`js/review.js:896`).
- The deck menu is a proper `role="menu"` with arrow keys (`js/decks.js:337-346`).
- Focus moves on purpose through the review: card, then answer, then next card.
- Motion: progress bars and the recorder dot respect `prefers-reduced-motion`.
- Forced colors: text boxes switch to `Highlight` outlines (`css/styles.css:295-296`).
